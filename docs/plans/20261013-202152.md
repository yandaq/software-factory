# Plan — watch-folder (todo/doing/done) prompt source

## Outcome

`sf` can start runs from a folder instead of a prompt string. Given a folder, the factory creates `todo/`, `doing/`, `done/` inside it, then monitors `todo/` indefinitely. Each Markdown file dropped into `todo/` becomes one run's prompt: it moves to `doing/` while the run executes and to `done/` when the run succeeds. Runs are strictly serial (one at a time); when `todo/` holds several files the oldest is taken first. The monitor runs until the user quits (Ctrl+C). `sf run`, `sf resume`, `sf improve` and `sf dashboard` behaviour is unchanged.

## Command shape (decision)

New Typer command, leaving `sf run` intact:

```
sf watch --target <path> <folder> [--approve-plan]
```

`<folder>` is the positional that replaces the prompt argument. Rationale: keeps `sf run`'s existing contract and keeps `cli.py` thin. A `--watch` option on `run` was the rejected alternative; if the user later insists on one command, `watch` becomes a thin alias.

## New module: `src/sf/mailbox.py`

Single responsibility: the folder queue. No workflow, git or harness knowledge. Public surface (names indicative; implementer may adjust):

- idempotent creation of `todo`/`doing`/`done` (`parents=True`)
- candidate listing: regular files directly in `todo/` whose suffix is `.md` case-insensitively (same convention as `target.discover_documentation`); subdirectories and other extensions ignored; ordered **oldest first by modification time, ties broken by filename**
- claim: move a file into `doing/`, disambiguating deterministically (counter or run-id prefix) if the name already exists
- complete: move the claimed file into `done/` with content unchanged, same collision handling
- settle guard: a file is claimable only after it has been unmodified for a short interval, so a half-written drop is never claimed
- monitor loop: repeatedly take the oldest claimable file until interrupted; injectable poll interval/sleep and an injectable per-file execution callback so tests never sleep or run forever

Monitor loop contract:
- claim → execute → move to `done/` only on run success
- on failure/abort the file **stays in `doing/`** (no auto-retry, so a broken prompt cannot loop forever); the monitor logs and continues with the next file
- if the factory `RunLock` is held by another `sf` process, leave the file in `todo/`, note it and keep polling (no crash)
- `KeyboardInterrupt` ends the monitor cleanly

## Steps

1. **Unique run ids** — `src/sf/workflow.py` (`new_run`): run ids stay `YYYYMMDD-HHMMSS` but creation must not reuse an existing `runs/<id>` directory (append a numeric suffix until free). Without this, two runs started inside one second — which the monitor makes possible — would share a run directory, state file and event stream. `sf/<run-id>` branch names and historical run ids are unaffected.
   *Test* (`tests/test_workflow.py`): two `new_run` calls in the same second yield distinct run ids/directories and independently loadable `run-state.json`.

2. **Queue module** — `src/sf/mailbox.py` (new), `tests/test_mailbox.py` (new): layout creation, candidate ordering, settle guard, claim/complete moves, collision-safe names. No workflow imports.
   *Tests:* folders created when absent and left untouched when present; oldest-by-mtime then filename ordering; `.md`/`.MD` accepted while `.txt`, no-suffix files and subdirectories are ignored; a file modified inside the settle window is not claimed while an older-mtime file is; claim empties `todo/` into `doing/`; complete lands the file byte-for-byte in `done/`; two same-named drops produce two distinct files in `done/`.

3. **Monitor loop** — `src/sf/mailbox.py`, `tests/test_mailbox.py`: implement the loop against an injected per-file executor and injected sleep.
   *Tests (stub executor, no model calls):* each `todo/` file is executed exactly once with its content passed as the prompt; the next file is claimed only after the previous executor returns (assert `doing/` empty at each claim → one run at a time); a raised execution error leaves that file in `doing/`, records the failure and still processes the next file; a busy `RunLock` keeps the file in `todo/` and the loop retries after release; `KeyboardInterrupt` from the injected sleep returns normally.

4. **CLI wiring** — `src/sf/cli.py`: add `watch`: `_factory()` check, `--target` (existing directory) and `<folder>` (created if missing, rejected if a file); resolve the target once up front so a bad target fails fast rather than failing every file. The per-file executor acquires `RunLock` **per run** (free between runs so `sf resume` works), builds the run via `new_run` from the file's content and runs `LiveDisplay` + `TerminalHuman` + `Workflow` exactly like `_execute`. Print the absolute `todo`/`doing`/`done` paths on start. On claim/complete/failure print a note naming file, run id and, for failures, the `sf resume <run-id>` hint and that the file stays in `doing/`. Per-run failures never exit the process; Ctrl+C exits 0. `--approve-plan` passes through; default `False`.
   *Test* (end-to-end in `tests/test_mailbox.py`) using the existing `factory`/`target`/`fake_pi` fixtures and the scripted fake imported from `test_workflow.py` (import helpers rather than duplicate them): drop two prompt files, run the monitor with a short poll interval, assert one completed run per file, `runs/<id>/prompt.md` equal to each file's content, both files present unchanged in `done/`, the fake-pi change merged to the target trunk, and an empty `doing/` at the end.
   *Runtime check:* `uv run sf watch --help` lists the command; `uv run sf --help` still lists run/resume/improve/dashboard.

5. **Observability** — `src/sf/mailbox.py` via the existing `Run.log` emitter: per-run `sf`-source events `mailbox_claimed` (file name, watch root), `mailbox_completed` and `mailbox_failed` (file name, outcome), so `events.jsonl` and the dashboard's sf lane show which file produced the run and where it went. No dashboard code change (it already lists all `source: "sf"` events and `prompt.md` is already an artefact).
   *Test:* the end-to-end test asserts the claim/complete events name the correct file; the failure test asserts a `mailbox_failed` event carries the failure text.

6. **Documentation** — `README.md` (usage line plus a short watch-folder paragraph), `docs/spec.md` (§3 CLI, §7 observability), `ARCHITECTURE.md` (module-table row for `mailbox.py` plus compromises: stdlib polling instead of a filesystem-watcher dependency; failure keeps the file in `doing/`; lock held per run, not per watch), `PLAN.md` (append a feature section with assumptions and validation evidence in the existing record style).

## Acceptance criteria

1. `sf watch --target <repo> <folder>` creates `todo`/`doing`/`done` when missing and requires no prompt argument.
2. A Markdown file dropped into `todo/` starts a run whose `runs/<id>/prompt.md` is that file's content; the file is in `doing/` during the run and in `done/`, unchanged, after success.
3. With several files in `todo/`, the oldest is taken first and runs never overlap (lock held during each run, released between runs).
4. The monitor keeps polling until Ctrl+C, which exits cleanly; a failed or aborted run does not stop it, leaves that file in `doing/` and is reported on the terminal and in that run's events with a resume hint.
5. Non-Markdown files, subdirectories and files still being written are not claimed.
6. `sf run`, `sf resume`, `sf improve` and `sf dashboard` are unchanged.

## Validation

- Focused: `uv run pytest -q tests/test_mailbox.py tests/test_workflow.py` — each new test observed failing for the expected reason before its step is implemented (VALIDATION.md §2).
- Lint: `uv run ruff check src tests`; `git diff --check`.
- Runtime: `uv run sf --help`, `uv run sf watch --help`.
- Full regression: `uv run pytest -q`, compared against the documented pre-existing baseline failures in `PLAN.md` (saved-planner configuration assumptions in `test_agents.py`; case-insensitive `AGENTS.md`/`agents.md` in `test_target.py`). Requirement: **no new failures**; those baselines are not fixed or weakened here.
- No live harness (Pi/Claude/Codex) calls: the fake-pi end-to-end test proves the user-visible journey deterministically. Dashboard browser checks are not applicable (no dashboard or static asset changes).

## Assumptions

- "Oldest" = oldest modification time, ties broken by filename; birth time is not used (unportable).
- A prompt file is any regular `*.md` (case-insensitive) directly in `todo/`; no recursion.
- `done/` means "run succeeded". Failed/aborted prompts stay in `doing/` for inspection and `sf resume`; there is no fourth folder and no automatic retry (the request fixed three folders, and `sf resume` does not move mailbox files). Retrying a failed prompt means dropping the file into `todo/` again as a fresh run.
- The watch process is interactive: plan approval and loop-cap prompts behave as in `sf run`. Ctrl+C mid-run leaves that run resumable and its file in `doing/`.
- Polling (default ~2 s module constant, no CLI flag) is acceptable; adding `watchdog` is out of scope per AGENTS.md §9.
- Monitor-level messages live on the terminal plus each run's `events.jsonl`; the factory has no factory-wide log file and adding one is out of scope.

## Risks

- The run-id `-N` suffix touches all run creation; mitigated by step 1's test and by historical run directories being untouched.
- A permanently failing prompt clutters `doing/` and needs manual clearing; accepted over infinite retries.
- Empty or whitespace-only prompt files are treated as valid prompts and passed to the planner (no special-casing requested).
